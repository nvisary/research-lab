# `lab/` — движок ручных исследований

Точка входа для всей ручной research-работы. Заменяет прежний уклад
`notebooks/<line>/_lab.py`, где вспомогательный модуль копипастился в каждую
линию и разошёлся на шесть версий, окна переопределялись в каждом ноутбуке, а
дисциплина против лукахеда существовала как призыв к внимательности.

Старые линии заархивированы в [`notebooks/_archive/`](../notebooks/_archive/README.md)
и доступны только на чтение. Новые живут в `lab/lines/<name>/`.

## Почему движок вообще появился

Три линии подряд умерли от лукахеда, и каждый раз его находили через два-три
ноутбука после того, как он въехал — то есть уже после того, как на нём было
построено здание:

| линия | вектор | цена |
|---|---|---|
| `pump` | якорь события = минута с максимальным ростом, выбранная задним числом | снесены +1.67%/сделку, +77% портфель, вывод в бот |
| `pump_dump_v2` | веса траншей нормированы на реализованную длину кластера: цена честная, размер знает будущее | линия закрыта целиком, headline 6.2x / Sharpe 3.04 оказался неисполним |
| `pump_dump_v3` | `merge(..., how='inner')` с таблицей, построенной по условию «дошёл до +5%» | две ретракции подряд в nb03 |

Общее у всех трёх: величина из будущего попадала **не в формулу доходности,
а в выбор** — какой момент считать событием, какой размер поставить, какие
строки оставить. Формулы при этом проверялись и были верны.

Поэтому здесь дисциплина выражена кодом. Не потому, что исследователь
невнимателен, а потому, что этот класс ошибок невидим по построению: строка
`how='inner'` выглядит как техническая склейка, а не как фильтр по будущему.

В ноутбуке:

```python
import sys; sys.path.insert(0, r"C:/projects/researchlab")
import lab
from pathlib import Path

print(lab.metrics.by_window(liquid.df, "pnl240"))
print(liquid.provenance())
```

## Контракт `asof` — центральная идея

У каждой колонки книги объявлено, **когда она становится известна**, в минутах
относительно входа:

- `CAUSAL` (0 или отрицательное) — известна в момент решения. Признаки бара-триггера,
  ликвидность, символ, час суток. По таким колонкам **можно** отбирать, группировать,
  сортировать, обучать модель.
- `outcome(h)` — известна через `h` минут после входа. Доходность, реализованная
  длина кластера, факт срабатывания стопа. По таким колонкам **только измерять**.

Проверка не декларативная: `book.where()` передаёт в ваш предикат рекордер,
который запоминает каждое обращение к колонке и сверяет его со схемой. Попытка
отфильтровать по исходу падает в момент написания фильтра.

Ловушка, которую это закрывает, тоньше, чем кажется. В книге v3 колонка `k` —
число баров-триггеров в кластере — выглядит как обычный признак события. Но она
известна только после конца кластера, и нормировка на неё убила v2. В схеме она
объявлена как `outcome(1)`, и попытка `where(lambda c: c.k >= 3)` блокируется.

## Что проверяет `lab.audit(book)`

| проверка | откуда взялась |
|---|---|
| у каждой колонки объявлен `asof` | без этого рекордер слеп |
| вход строго позже сигнала | `pump` nb09_2: вход на баре, определяющем сигнал, забирает движение этого бара |
| `frac` объявлен и ≤ 1 | `pump_dump_v2` nb07: доля реально развёрнутого капитала |
| нет задвоенных событий | задвоение тихо завышает и доходность, и n |
| события попадают в объявленные окна | иначе часть выборки молча выпадает из всех разбивок |

Плюс печатается провенанс: как из полной книги получилась текущая выборка, с
процентом потерянных строк на каждом шаге и обязательным `why`.

## Проверка самого движка

`lab/tests/test_audit.py` — синтетика, где ответ известен по построению.
`lab/tests/retro_v3.py` — честнее: берёт настоящие книги `pump_dump_v3` и
проверяет, ловит ли движок тот самый баг, который в своё время заметили
только через два ноутбука. Результат прогона:

```
ПРОВЕРКА 1. аудит книги как есть          → найдена 1 проблема (нет frac)
ПРОВЕРКА 2. отбор по реализованному k     → заблокирован
ПРОВЕРКА 3. отбор по pnl240               → заблокирован
ПРОВЕРКА 4. inner join из nb03            → заблокирован (−10.9%, 33 760 → 30 064)
ПРОВЕРКА 5. тот же джойн, объявленный     → пропущен, сужение в провенансе
ИТОГ: 5/5
```

Ради этого прогона намеренно сохранены кеши `notebooks/_archive/pump_dump_v3/_out/`
(38 МБ) — регрессия на реальных данных стоит этого места. Скрипт корректно
пропускается, если книг нет.

## Производительность

Замер на 673 символах за 2024-01..2026-08: один проход — 5.5 минут, из них
3.2 на чтение parquet и 2.3 на счёт, всё в один поток при 32 ядрах. Четыре
билдера линии v3 платили это независимо друг от друга — 22 минуты.

`lab.scan()` раздаёт символы процессам: тот же проход укладывается примерно в
сорок секунд. Важно не время ожидания, а режим работы — при пяти минутах на
прогон вопросы к данным копятся в батч и часть просто не задаётся.

Ограничение: функция уходит в процессы через pickle, поэтому её нужно
определять в модуле `_build_*.py`, а не в ячейке ноутбука. Это не досадность,
а ровно тот уклад, который и так себя оправдал: тяжёлое считается билдером и
кладётся в parquet с манифестом, ноутбук читает готовое.
